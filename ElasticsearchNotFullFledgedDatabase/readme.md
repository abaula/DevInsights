# Elasticsearch (ES) не является полноценной базой данных

Elasticsearch (ES) не является полноценной базой данных, и его использование в качестве основного хранилища (Primary Data Store) — одна из самых частых и опасных архитектурных ошибок. Несмотря на то, что ES умеет хранить JSON-документы и быстро искать по ним, он создавался как поисковый движок, а не СУБД.

Главный «камень преткновения», с которым неизбежно сталкиваются разработчики при попытке сделать из Elasticsearch базу данных — это жесткое ограничение на вывод в 10 000 записей (параметр index.max_result_window).

Ниже подробно разобрано, почему это ограничение существует, как оно ломает привычную работу с данными и какие еще подводные камни ждут тех, кто путает поиск с хранением.

## Проблема 10 000 записей: почему пагинация в ES «ломается»

В традиционных реляционных базах данных (PostgreSQL, MySQL) вы можете легко запросить миллионную строку с помощью конструкции OFFSET 1000000 LIMIT 10. База данных просто отсчитает нужный сдвиг.

В Elasticsearch классическая пагинация (from + size) свыше 10 000 документов заблокирована по умолчанию.

## Почему так сделано?

Elasticsearch — это распределенная система. Ваши данные размазаны по разным частям (шардам) кластера. Когда вы просите ES вернуть документы с 9 990 по 10 000, происходит следующее:

   1. Координационный узел отправляет запрос на все шарды.
   2. Каждый шард выбирает у себя топ-10 000 документов и отправляет их на координационный узел.
   3. Если у вас 5 шардов, координационный узел должен принять 50 000 документов, загрузить их в оперативную память, отсортировать между собой, отдать вам 10 штук, а остальные 49 990 выбросить.

Итог: Запрос глубоких страниц через from + size экспоненциально увеличивает нагрузку на память (RAM) и процессор (CPU). Если убрать лимит в 10 000, тяжелый запрос пользователя или веб-краулера может мгновенно уронить весь кластер по ошибке Out of Memory (OOM).

## Как это обходят и почему это неудобно для БД?

Чтобы достать данные свыше лимита, приходится использовать костыли или специальные API:

* search_after: требует обязательной сортировки по уникальному полю (например, _id) и передачи значения последней строки в следующий запрос. Это делает невозможным прыжок сразу на 50-ю страницу интерфейса — листать можно только строго по порядку (как в ленте соцсетей).
* Scroll API: делает «снимок» состояния данных на момент запроса. Он эффективен для выгрузки (дампа) данных, но сохранение контекста поиска сильно расходует ресурсы и не подходит для живых пользовательских запросов в реальном времени.

## Другие критические причины не использовать ES как основную БД

Ограничение в 10 000 строк — лишь верхушка айсберга. Есть и другие фундаментальные отличия Elasticsearch от нормальных баз данных:

## 1. Отсутствие ACID-транзакций
Elasticsearch не поддерживает транзакции. Вы не можете объединить несколько изменений в атомарный блок (чтобы либо выполнилось всё, либо ничего). Если в процессе записи пяти документов произойдет сбой на третьем, система останется в промежуточном, несогласованном состоянии. Для финансовых или критически важных данных это недопустимо.

## 2. Задержка при чтении (Near Real-Time)
ES — это система почти реального времени. Документ после записи не доступен для поиска мгновенно. Он должен пройти процесс сегментации и очистки индекса (Refresh), что занимает по умолчанию около 1 секунды. В полноценных БД данные доступны для чтения сразу после коммита.

## 3. Высокое потребление ресурсов и оверхед
Elasticsearch строит под капотом инвертированные индексы для полнотекстового поиска. Это требует огромного количества оперативной памяти и дискового пространства. Хранить там «сырые» данные, по которым не нужен текстовый поиск — экономически невыгодно.

## 4. Риск потери данных (Data Loss)
Исторически Elasticsearch создавался с приоритетом на скорость поиска и доступность, а не на абсолютную надежность хранения. При падении нод или сетевом разделении кластера (split-brain) существует ненулевой риск потерять последние записанные данные, которые еще не успели синхронизироваться.

## Правильная архитектура: CQRS подход

Правильный паттерн использования Elasticsearch — это его работа в связке с реляционной (PostgreSQL, MySQL) или NoSQL (MongoDB, Cassandra) базой данных.

   1. Основная БД хранит эталонные данные («источник правды»), обеспечивает транзакции, строгую консистентность и позволяет выгружать любые объемы данных по ID или через курсоры.
   2. Elasticsearch выступает в роли вторичного хранилища (индекса для поиска). Данные реплицируются в него из основной БД. В ES идут только те запросы, где нужен сложный полнотекстовый поиск, автодополнение или сложная аналитика.

## Вывод

Попытка использовать Elasticsearch как базу данных общего назначения похожа на использование гоночного болида для перевозки кирпичей. Он спроектирован для мгновенного нахождения иголки в стоге сена, но совершенно не приспособлен для того, чтобы этот стог регулярно и упорядоченно перекладывать с места на место большими порциями.
