# Форматированный Output в LLM: механика, контроль и оптимизация для локального инференса

__Status: Draft__

Большие модели (70B+) сегодня отлично справляются с форматированным выводом «из коробки». Им достаточно краткого промпта, и они стабильно генерируют валидный JSON без дополнительной настройки. Проблема возникает, когда речь заходит о локальном инференсе на слабых или средних моделях (1B–7B, квантование Q4/Q5), где каждый рубль на инфраструктуре и каждый такт процессора имеют значение. В таких условиях надежда на «умный промпт» быстро разбивается о реальность: модель ломает скобки, добавляет пояснительный текст, забывает закрывающие кавычки или уходит в галлюцинации.

Цель этой статьи — разобрать механику форматированного вывода на уровне токенов и сэмплера, показать, как заставить даже слабую локальную модель генерировать строго структурированные данные, и дать практические инструменты для интеграции в .NET-стек. Мы не будем соревноваться с облачными гигантами — мы научимся экономить, контролируя генерацию на уровне движка.

---

## 1. Выбор модели для извлечения структурированных данных

Не существует «специальной JSON-модели». Способность к структурированному выводу зависит от доли кода, конфигураций, таблиц и технических документов в обучающей выборке, а также от качества инструктивного тюнинга. Облачные флагманы обучены на сотнях терабайт размеченных данных, поэтому им хватает параметра `response_format: json_schema`. Локальные модели ≤7B, особенно после чат-тюнинга на диалогах, часто «забывают» синтаксис при генерации длинных последовательностей.

Выбор здесь сводится к инженерному компромиссу: большие веса дают встроенную стабильность, но требуют дорогой инфраструктуры; маленькие экономят ресурсы, но нуждаются во внешнем контроле вывода. Для локального инференса ключевым становится не размер модели, а наличие рантайма, поддерживающего принудительное ограничение грамматики. На практике для извлечения параметров оптимальны модели с явной тренировкой на коде/структурированных данных (семейства Qwen2.5, Llama 3.1, Mistral Small) в сочетании с движком, умеющим маскировать логиты.

*Краткий пример концепции:*
```csharp
// ❌ Подход "на авось" (полагается только на промпт и вероятности модели)
var naiveParams = new InferenceParams { Temperature = 0.7f };
var naiveOutput = executor.Infer("Верни JSON с полями age и name.", naiveParams);
// Для модели ≤7B результат часто содержит пояснения, ломает скобки или игнорирует формат.

// ✅ Инженерный подход (структура задаётся рантаймом, а не "интеллектом" модели)
var schema = @"{ ""type"": ""object"", ""properties"": { ""age"": {""type"":""number""} } }";
var stableParams = new InferenceParams
{
    Grammar = LlamaGrammar.FromJsonSchema(schema),
    Temperature = 0.0f
};
var stableOutput = executor.Infer("Извлеки возраст из текста.", stableParams);
// Результат гарантированно валиден: рантайм физически блокирует недопустимые токены.
```

## 2. Грамматическое ограничение на уровне сэмплера (Constrained Sampling)

Промпт вида «верни только JSON» работает на вероятностях. Грамматическое ограничение работает на уровне физики процесса генерации. На каждом шаге авторегрессии модель выдаёт вектор сырых логитов для всего словаря (~50–150 тыс. токенов). Перед тем как сэмплер сделает выбор, движок применяет конечный автомат (FSM), собранный из вашей схемы.

Автомат проверяет текущее состояние структуры и присваивает логитам всех недопустимых токенов значение `-∞`. Вероятность их выбора становится нулевой. Сэмплер (даже с `temperature=0.7`) физически не может выдать токен, ломающий грамматику. Это даёт 100% структурную гарантию без постобработки и ретраев. В отличие от промпт-инжиниринга, где успех зависит от формулировок и удачи, здесь результат детерминирован математически.

## 3. Формат и внутренняя работа с GBNF

В экосистеме `llama.cpp` и его обёрток грамматика описывается на языке GBNF (GGML Backus-Naur Form). Это диалект EBNF, оптимизированный под токенизацию: правила работают не с символами, а с токенами модели. При старте инференса строка правил компилируется в детерминированный конечный автомат с поддержкой стека. Движок заранее строит таблицу соответствия: какие токены из словаря допустимы в каждом состоянии.

Писать GBNF вручную редко требуется — современные рантаймы конвертируют стандартную JSON Schema во внутренний формат автоматически. Однако конвертация не всесильна: сложные конструкции `oneOf`, `patternProperties` или вложенные `dependentSchemas` могут раздуть автомат, что увеличивает задержку на каждом шаге. Главный риск — дедлок, когда грамматика запрещает все токены, которые модель «хочет» выдать. Решается упрощением схемы, снижением температуры или явным указанием альтернативных путей в правилах.

*Минимальное правило:*
```gbnf
root  ::= "{" key ":" value "}"
key   ::= "\"" [a-z]+ "\""
value ::= [0-9]+
```

## 4. Управление циклом инференса: доступ к логитам и пошаговая генерация

Возможность влиять на вывод зависит не от весов модели, а от архитектуры рантайма. Стандартные методы вроде `executor.Infer()` скрывают процесс генерации в «чёрном ящике». Для тонкой логики, кастомных фильтров или интеграции с внешними системами состояния требуется **разорванный цикл** (stepwise inference), где каждый шаг явно разделён на: вычисление логитов, применение ограничений, сэмплирование и обновление контекста.

В `LLamaSharp` это реализуется через низкоуровневый доступ к `LLamaContext`. Рантайм предоставляет методы `Eval()` (forward pass), `GetLogits()` (сырые веса), `Grammar.ApplyMask()` (фильтрация) и `Sample()` (выбор токена). Ниже показан концептуальный паттерн ручного цикла, который демонстрирует, как движок управляет генерацией под капотом.

*Пример разорванного цикла (LLamaSharp нижнеуровневый паттерн):*
```csharp
var state = new LLamaState();
var promptTokens = context.Tokenize(prompt);
state.Tokens.AddRange(promptTokens);

var grammar = LlamaGrammar.FromJsonSchema(schema);
var sampler = new LLamaSampler(temperature: 0.0f, top_p: 1.0f);

for (int step = 0; step < maxTokens; step++)
{
    // 1. Forward pass: вычисление логитов на основе текущего контекста
    context.Eval(state.Tokens, state, n_past: promptTokens.Count);
    var logits = context.GetLogits(-1); // логиты последнего токена

    // 2. Применение грамматики: маскирование недопустимых токенов (-∞)
    var allowed = grammar.GetAllowedTokens(state);
    var maskedLogits = logits.Mask(allowed);

    // 3. Сэмплирование: выбор следующего токена из разрешённых
    var nextToken = sampler.Sample(maskedLogits);
    if (nextToken == -1 || grammar.IsTerminal()) break;

    // 4. Инжект токена и обновление состояния (позиции, KV-cache обновляются автоматически)
    state.Tokens.Add(nextToken);
    grammar.AcceptToken(nextToken);
}
```
В продакшене этот цикл абстрагирован в `InteractiveExecutor` или `StatelessExecutor`, но понимание его структуры критично: именно здесь происходит синхронизация токенизатора, грамматики и сэмплера. Если рантайм не предоставляет доступ к `Eval`/`GetLogits`/`Sample`, значит, он не поддерживает ручное вмешательство в цикл генерации.

## 5. Влияние токенов форматирования на авторегрессию

Любая современная LLM — **авторегрессионная модель**. Она предсказывает следующий токен, опираясь на всю предыдущую последовательность. Каждый сгенерированный токен:
- Обновляет `KV-cache` (скрытые состояния ключей и значений в механизме внимания)
- Сдвигает `position_id` (влияет на позиционное кодирование, например RoPE)
- Перераспределяет веса внимания в головах трансформера

Это означает, что выбор токена форматирования **не нейтрален**. Например, выбор между `}` и `},` меняет семантическую траекторию: первый закрывает объект, второй сигнализирует системе «ожидается следующий ключ». Если грамматика принудительно вставляет токен, который модель статистически не ожидала (логит близко к `-2.0` или ниже), происходит **рассинхрон распределения**. Модель получает контекст, смещённый относительно её тренировочного паттерна, и на следующих шагах может начать генерировать повторы, пропускать значения или уходить в «болтовню».

Современные движки решают эту проблему **не добавлением бонусных весов** к структурным токенам. Ручное изменение логитов искажает относительные вероятности внутри допустимого множества и усиливает каскадный дрейф. Вместо этого применяется:
1. **Маскирование** (`-∞` для недопустимых путей)
2. **Детерминированный выбор** (`temperature=0.0` схлопывает распределение до топ-1)
3. **Синхронное обновление** `KV-cache` и позиций, чтобы следующий `Forward()` видел валидный контекст

Модель не «знает», что токен был выбран грамматикой. Для неё это обычная последовательность. Ограничение происходит *до* сэмплирования, а не после. Если после структурного токена логиты следующего шага стабильно уходят в отрицательные значения, это сигнал: схема слишком сложна для данной модели, и требуется упрощение, а не «подкрутка» весов.

*Параметры стабилизации в .NET:*
```csharp
var @params = new InferenceParams
{
    Temperature = 0.0f,      // детерминизм в структурных точках
    RepeatPenalty = 1.15f,   // защита от зацикливания на скобках
    TopP = 1.0f,
    // LogitBias не используется для форматирования — он только для семантики
};
```

## 6. Гибридный подход: `sampling + relaxed syntax` для слабых локальных моделей

Для моделей ≤3B в квантовании Q4/Q5 даже строгий JSON может вызывать перегрузку механизма внимания. Плоский формат `ключ значение\n` (или `relaxed syntax`) стал инженерным компромиссом, заменяющим вложенность на предсказуемость.

**Почему это работает на слабых моделях:**
- **Минимум служебных токенов:** Нет `"`, `:`, `,`, `{`, `}`. Модель не тратит вычислительные ресурсы на синтаксические маркеры, которые в чат-тюнинге часто ассоциированы с инструкциями, а не с генерацией данных.
- **Совпадение с тренировочными данными:** Логи систем, `.env`-файлы, таблицы, технические отчёты и `key=value` конфиги составляют значительную часть открытого веба. Распределение вероятностей слабых моделей ближе к этому формату, чем к строгому JSON.
- **Компактная грамматика:** FSM для `key value\n` занимает ~50–100 состояний против 500–2000 для вложенного JSON. Проверка на каждом шаге почти не даёт оверхеда на CPU.
- **Отсутствие разрывов контекста:** Плоская структура не требует отслеживания глубины вложенности. Механизм внимания работает в одном контекстном окне без «перепрыгивания» между уровнями объектов.

**Правила продакшен-формата:**
```text
- Разделитель: один пробел или `:::` (если значения могут содержать пробелы)
- Ключи: предопределённый словарь, без пробелов, только `[a-zA-Z0-9_]`
- Значения: занимают всё до `\n` или следующего ключа
- Пропуски: явно указываются как `__NULL__` или пропускаются строкой
- Завершение: фиксированный маркер `===END===` или ограничение по `MaxTokens`
```

**Ограничения и как их обходить:**
| Проблема | Решение |
|----------|---------|
| Нет вложенности/массивов | Разбивайте на отдельные ключи (`items_count`, `item_1_name`, `item_1_val`) или используйте JSON только для сложных сущностей |
| Пробелы в значениях | Используйте `:::` как разделитель или разрешите кавычки только для строковых полей в GBNF |
| Дубликаты ключей | `RepeatPenalty = 1.15f` + дедупликация при парсинге (`TryAdd` в `Dictionary`) |
| Только синтаксическая типизация | Грамматика проверит `2024-13-45` как строку/число, но не календарную корректность. Требуется `DateTime.TryParse` или `Range` в .NET |

*Пример правила для relaxed syntax:*
```gbnf
root  ::= (line "\n")+
line  ::= key " " value
key   ::= [a-zA-Z_][a-zA-Z0-9_]*
value ::= [^ \t\n\r]+
```

Для извлечения 10–20 плоских параметров на edge-устройствах это часто оптимальный баланс между стабильностью, скоростью и затратами. Формат не масштабируется на сложные схемы, но экономит до 30–40% времени инференса и снижает частоту `JSONDecodeError` до нуля.

## 7. Примеры на .NET с LLamaSharp

Ниже приведены готовые паттерны для продакшен-интеграции. Все примеры используют `LLamaSharp` (обёртка над `llama.cpp`), но логика применима к любому рантайму с поддержкой GBNF/JSON Schema.

### 7.1. Базовая настройка и загрузка модели
```csharp
using LLama;
using LLama.Common;

// Параметры загрузки (адаптируйте под ваше железо)
var modelParams = new ModelParams("models/qwen2.5-3b-instruct.Q4_K_M.gguf")
{
    ContextSize = 4096,
    GpuLayerCount = 20,      // оффлоад на GPU
    Seed = 1234              // воспроизводимость
};

using var weights = new LLamaWeights(modelParams);
using var context = weights.CreateContext(modelParams);
using var executor = new StatelessExecutor(weights, modelParams);
```

### 7.2. Генерация с JSON Schema (Constrained Sampling)
```csharp
var jsonSchema = @"{
  ""type"": ""object"",
  ""properties"": {
    ""temperature"": { ""type"": ""number"" },
    ""pressure"": { ""type"": ""integer"" },
    ""status"": { ""type"": ""string"", ""enum"": [""normal"", ""warning"", ""critical""] }
  },
  ""required"": [""temperature"", ""pressure"", ""status""]
}";

var grammar = LlamaGrammar.FromJsonSchema(jsonSchema);
var inferenceParams = new InferenceParams
{
    Grammar = grammar,
    Temperature = 0.0f,
    TopP = 1.0f,
    RepeatPenalty = 1.1f,
    MaxTokens = 256,
    AntiPrompts = new List<string> { "\n\n", "</s>" }
};

var prompt = "Датчик показывает: температура 23.7, давление 1015 мбар, состояние warning.";
var output = executor.Infer(prompt, inferenceParams);
var resultText = string.Join("", output);

// Парсинг в строго типизированный объект
var parsed = System.Text.Json.JsonSerializer.Deserialize<SensorData>(resultText);
```

### 7.3. Генерация с Relaxed Syntax (`ключ значение`)
```csharp
var relaxedGbnf = @"
root  ::= (line ""\n"")+
line  ::= key "" "" value
key   ::= [a-zA-Z_][a-zA-Z0-9_]*
value ::= [^ \t\n]+
";

var grammarRelaxed = LlamaGrammar.FromString(relaxedGbnf);
var inferenceParamsRelaxed = new InferenceParams
{
    Grammar = grammarRelaxed,
    Temperature = 0.1f,      // небольшая стохастичность допустима для значений
    TopP = 0.95f,
    RepeatPenalty = 1.15f,
    MaxTokens = 128
};

var promptRelaxed = "Извлеки параметры в формате: ключ значение\\n";
var outputRelaxed = executor.Infer(promptRelaxed, inferenceParamsRelaxed);
var textRelaxed = string.Join("", outputRelaxed);

// Быстрый парсинг
var dict = new Dictionary<string, string>();
foreach (var line in textRelaxed.Split('\n', StringSplitOptions.RemoveEmptyEntries))
{
    var parts = line.Split(' ', 2);
    if (parts.Length == 2) dict[parts[0].Trim()] = parts[1].Trim();
}
```

### 7.4. Валидация и постобработка в .NET
Грамматика гарантирует синтаксис, но не бизнес-логику. Всегда валидируйте типы после парсинга:
```csharp
if (dict.TryGetValue("temperature", out var tStr) && double.TryParse(tStr, out var t))
{
    if (t is < -50 or > 150) throw new ArgumentOutOfRangeException("Неверный диапазон температуры");
}

if (dict.TryGetValue("status", out var s) && !Enum.TryParse<StatusType>(s, true, out _))
{
    throw new InvalidDataException("Неизвестный статус системы");
}
```

### 7.5. Отладка и рекомендации для продакшена
- **Логирование грамматики**: включите `LoggingLevel = LogLevel.Debug` в `LLamaContext` для отслеживания `grammar accept: failed` (признак дедлока).
- **Разделение потока**: не смешивайте чат-историю и структурный вывод. Используйте `StatelessExecutor` для каждого запроса или очищайте `KVCache`.
- **Fallback-механизм**: если генерация обрывается на середине строки, уменьшите `MaxTokens`, упростите схему или добавьте `AntiPrompts`.
- **Производительность**: на CPU-инференсе разница между `temperature=0.0` и `temperature=0.7` с грамматикой незаметна, но детерминированный режим снижает нагрузку на сэмплер и ускоряет обработку детерминированных путей.

---

Форматированный вывод — это не магия промптов, а контролируемый процесс на уровне токенов, сэмплера и конечного автомата. Понимание этой механики позволяет перенести ответственность за структуру с «интеллекта» модели на рантайм, что критично для экономичного локального инференса. Выберите схему под задачу, настройте `InferenceParams` под ресурсы, и даже небольшая модель станет надёжным компонентом вашего пайплайна.
