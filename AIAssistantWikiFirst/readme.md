# AI ассистенты — подход wiki-first

В современных проектах объём кодовой базы растёт экспоненциально, а AI-ассистенты становятся неотъемлемой частью рабочего процесса. Однако без единого источника знаний каждый разработчик (и каждый AI-агент) вынужден изучать проект с нуля, тратя лимиты контекстного окна, время и ресурсы. Подход **wiki-first** решает эту проблему, превращая документацию в живой, автоматически поддерживаемый центр знаний, который диктует правила работы как людям, так и AI.

> 📌 **Примечание:** Все примеры структуры, имена файлов (`QWEN.md`, `.qwen/skills/`) и рабочие потоки в этой статье приведены для экосистемы **QWEN**. Сама методология универсальна и легко адаптируется под любого AI-агента, способного работать с инструкциями в формате Markdown.

---

## 🔍 Что такое wiki-first?

**Wiki-first** — это методология, при которой перед любой работой с кодом (написание фичи, ревью, рефакторинг, архитектурное решение) разработчик или AI-агент **обязан** сначала изучить wiki-документацию проекта (`docs/wiki/`).

Ключевой принцип:
> `Wiki = обзор, Код = детали`

В wiki хранятся сжатые, структурированные знания: архитектура системы, принятые паттерны, зависимости сервисов, конвенции именования и правила DI. Конкретные сигнатуры методов, SQL-запросы или ассерты в тестах ищутся только в коде, если wiki не покрывает задачу.

---

## 🚀 Преимущества подхода

| Аспект | Без wiki-first | С wiki-first |
|--------|----------------|--------------|
| **Погружение в проект** | Каждый изучает код с нуля | Готовый обзор за 5 минут |
| **Хранение знаний** | Знания остаются в головах разработчиков | Знания централизованы в wiki, доступны всем |
| **Онбординг** | Новички тратят дни на разбор кода | Новички читают wiki → часы вместо дней |
| **Работа AI-агентов** | Тратят контекст на сканирование тысяч строк | Читают краткие wiki-страницы, экономят токены и время |
| **Актуальность документации** | Wiki отстает от кода, быстро «тухнет» | Wiki обновляется автоматически после каждого изменения |
| **Соблюдение стандартов** | Разработчики нарушают паттерны по незнанию | AI и люди следуют единым правилам из wiki |

## 🛠 Как установить wiki-first в свой проект

Для быстрой и корректной настройки используется шаблон [WIKI_FIRST_TEMPLATE.en.md](WIKI_FIRST_TEMPLATE.en.md). Он предназначен **для выполнения AI-агентом**, который создаст всю инфраструктуру знаний и навыки автоматически.

### Шаг 1. Подготовка параметров
1. Скопируйте `WIKI_FIRST_TEMPLATE.en.md` в корень вашего репозитория.
2. Откройте файл и заполните таблицу `INPUT DATA` реальными значениями:

| Параметр | Пример |
|----------|--------|
| `project_name` | `WebArchiveBackend` |
| `project_description` | `Backend API для хранения и индексации веб-страниц` |
| `tech_stack` | `C#, .NET 8, gRPC, PostgreSQL, Dapper` |
| `docs_path` | `docs/` |
| `wiki_path` | `docs/wiki/` |
| `skills_path` | `.qwen/skills/` |
| `source_dirs` | `src/, tests/` |

### Шаг 2. Запуск AI-агента
Передайте заполненный файл вашему AI-ассистенту со следующим промптом:
> «Выполни инструкции из файла `WIKI_FIRST_TEMPLATE.en.md` строго по шагам. Создай структуру wiki, AI-навыки и главный файл правил. Не изменяй существующий код проекта. После создания структуры выполни Initial Ingest (Step 6).»

Агент автоматически:
1. Создаст директорию `docs/wiki/` и три базовых файла:
   - `index.md` — каталог всех wiki-страниц
   - `log.md` — журнал изменений (append-only)
   - `Wiki Format.md` — гайд по оформлению страниц
2. Сгенерирует три специализированных AI-навыка в `.qwen/skills/`:
   - `wiki-workflow` — управление знаниями (ingest, query, lint, post-change lint)
   - `code-contributor` — написание и модификация кода по стандартам
   - `code-architecture` — архитектурное ревью (SOLID, DI, слоистая архитектура)
3. Создаст `QWEN.md` в корне проекта с жёстким правилом wiki-first и иерархией источников: `docs/wiki/ > Project code`.

### Шаг 3. Первичный анализ проекта (Initial Ingest)
После создания структуры агент выполнит **Step 6** из шаблона:
- Просканирует директории с исходным кодом (`source_dirs`).
- Сформирует начальные wiki-страницы: `Architecture.md`, `Components.md`, `Database.md`, `Code Patterns.md`, `Testing.md`.
- Обновит `index.md`, добавив новые страницы в каталог.
- Добавит запись в `log.md` о начальной загрузке знаний.
- ⚠️ **Важно:** Wiki содержит только обзоры и относительные ссылки на файлы. Копирование кода из `.cs`, `.proto` или `.sql` файлов запрещено.

### Шаг 4. Верификация установки
После завершения работы агента проверьте результат по чек-листу:
- [ ] `QWEN.md` содержит правило wiki-first и приоритет источников
- [ ] В `docs/wiki/` созданы `index.md`, `log.md`, `Wiki Format.md`
- [ ] В `.qwen/skills/` находятся 3 файла `SKILL.md`
- [ ] Во всех навыках явно указано: `wiki > code`
- [ ] Сгенерированы базовые wiki-страницы по архитектуре, компонентам и паттернам
- [ ] `index.md` содержит ссылки на все созданные страницы
- [ ] `log.md` содержит запись о первом ingest с датой и описанием

## 🔄 Как работать с wiki-first после установки

| Роль | Правило |
|------|---------|
| **Разработчик** | Перед задачей → открой `docs/wiki/index.md`. После коммита → обнови wiki + добавь запись в `log.md`. |
| **AI-агент** | Любой запрос → сначала wiki. После изменения кода → post-change lint. Недостающие детали → читать код. |
| **Code Review** | Если PR не обновил wiki → запросить изменения. Wiki не должна расходиться с кодом. |

Типичный цикл работы AI-агента:
1. `Wiki-first` → читает `index.md` → находит релевантные страницы
2. `Query/Ingest` → уточняет детали в коде, если нужно
3. `Code` → пишет фичу/фикс по паттернам из wiki
4. `Post-Change Lint` → обновляет wiki и `log.md`
5. `Verify` → проверяет ссылки, frontmatter, соответствие коду

## 🔄 Жизнь wiki: поддержка, согласованность и эволюция навыков

Установка wiki-first — это не разовая настройка, а запуск живого процесса. Документация, оставленная без внимания, быстро превращается в «кладбище знаний». Чтобы подход приносил долгосрочную пользу, wiki должна постоянно обновляться, а AI-агент обязан выступать главным гарантом её согласованности и полноты.

### 🤖 Агент как хранитель целостности
После первоначальной настройки ответственность за актуальность wiki ложится на AI-агента. При каждом изменении кода агент должен автоматически запускать **post-change lint**: проверять, не противоречат ли существующие страницы новой реализации, обновлять описания затронутых компонентов и фиксировать изменения в `log.md`.

Требуйте от агента явного подтверждения синхронизации. Если коммит затрагивает архитектуру, конфигурацию или добавляет новые модули — агент обязан не просто поправить код, но и актуализировать wiki. Это превращает документацию из «дополнительной нагрузки» в неотъемлемую часть рабочего цикла. Без этого шага wiki быстро рассинхронизируется с кодом, и правило `wiki > code` потеряет смысл.

### 📖 Документирование комплексных сценариев
Настоящая сила wiki-first раскрывается, когда в базу знаний заносятся не только статические описания, но и **специфичные для проекта рабочие процессы**.

Например, добавление нового параметра конфигурации в вашем проекте может требовать правок в пяти разных местах: от `appsettings.json` до объектов DI-контейнера, DTO-моделей и миграций БД. Вместо того чтобы каждый раз объяснять это агенту заново, один раз оформите этот сценарий как отдельную wiki-страницу или раздел в `Паттерны кода.md`.

Как только сложный сценарий задокументирован в wiki, агент начинает выполнять его **уверенно, без галлюцинаций и пропусков шагов**. При запросе «Добавь параметр X» агент:
1. Находит инструкцию в wiki через `index.md`.
2. Чётко следует описанной последовательности изменений.
3. Автоматически обновляет wiki, если сценарий требует адаптации под новые реалии.

Чем больше «рутинных» и «забытых» сценариев вы формализуете в wiki, тем меньше времени тратится на микроменеджмент агента и тем выше стабильность результата.

### 🧠 Модельно-специфичная природа wiki
Разные LLM-модели по-разному структурируют мысли, выбирают приоритеты и формулируют инструкции. Это **не баг, а фича**. Когда агент сам формирует wiki в ходе начального анализа (`Initial Ingest`) или последующих обновлений, документация естественным образом «подстраивается» под его внутреннюю логику, токенизацию и паттерны внимания.

Модель будет гораздо точнее и увереннее следовать wiki, которую сгенерировала или курировала сама, чем документации, написанной другой моделью или человеком «под себя». Поэтому не стремитесь к идеальной «человеческой» стилистике на первых этапах. Главное — чтобы структура была однозначной, ссылки работали, а логика обновлений соблюдалась. Со временем вы заметите, что wiki становится «родным языком» вашего агента: он быстрее находит контекст, реже галлюцинирует и точнее выполняет комплексные задачи.

### 🛠 Эволюция навыков и правил
Навыки (`skills`), созданные на этапе установки, не высечены в камне. По мере роста проекта и накопления опыта работы с агентом, их необходимо адаптировать:
- Если агент часто упускает определённый тип проверок — добавьте соответствующее правило в `code-architecture` или `wiki-workflow`.
- Если появляются новые технологические стеки или паттерны — расширьте `code-contributor` примерами и конвенциями.
- Если wiki-структура становится слишком громоздкой — переработайте `index.md`, введите теги или разбейте монолитные страницы на тематические блоки.

Сам `QWEN.md` и файлы `SKILL.md` — это часть wiki-экосистемы. Их можно и нужно рефакторить, чтобы инструкции оставались точными, минимизировали потребление контекста и соответствовали текущему этапу зрелости проекта.

### 💡 Главный принцип: Wiki — это живой организм
Ключевая идея подхода заключается в следующем: **wiki нельзя просто создать, её нужно постоянно развивать**.
- **Поддерживайте актуальность:** каждая правка в коде → правка в wiki + запись в `log.md`.
- **Обогащайте контекст:** превращайте устные договорённости, баг-треки и сложные ручные процедуры в формализованные wiki-инструкции.
- **Развивайте агента:** адаптируйте навыки, уточняйте приоритеты и шлифуйте промпты под реальные задачи проекта.

Когда wiki становится единым источником правды, а агент выступает её активным куратором, команда получает масштабируемую систему знаний. Она не «тухнет» со временем, а набирает силу: чем больше вы в неё вкладываете, тем быстрее, точнее и увереннее работает AI, сокращая время на онбординг, код-ревью и исправление ошибок.

## 💡 Заключение

Подход wiki-first трансформирует документацию из «артефакта, который забывают обновлять» в **активный инструмент разработки**. AI-агенты, работающие по этим правилам, экономят контекст, строго соблюдают архитектурные стандарты и ускоряют доставку фич.

Установите wiki-first один раз через [WIKI_FIRST_TEMPLATE.en.md](WIKI_FIRST_TEMPLATE.en.md), интегрируйте его в CI/CD и onboarding — и получите масштабируемую систему знаний, которая растёт вместе с вашим проектом, а не превращается в legacy.
