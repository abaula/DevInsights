# От DNS до Service Mesh: управление адресацией и трафиком в распределённых приложениях

В эпоху монолитных приложений управление сетевым трафиком было тривиальной задачей. Приложение разворачивалось на сервере с фиксированным IP-адресом, а для доступа к нему настраивался один домен.

С переходом к микросервисной архитектуре и облачным кластерам всё изменилось. Сотни независимых контейнеров постоянно создаются, перезапускаются, масштабируются и умирают. У них нет фиксированных IP-адресов, а ручное обновление конфигураций сети стало невозможным.

Эта статья спроектирована как верхнеуровневый справочник, который поможет разработчику разобраться в эволюции подходов к управлению сетевым трафиком и адресацией в распределённых системах.

## Вводные понятия: Направления трафика (North-South и East-West)

Прежде чем переходить к технологиям, необходимо разобраться в фундаментальной терминологии, которую используют сетевые инженеры и архитекторы для разделения потоков данных в распределённых системах. Весь сетевой трафик делят на два направления:

**North-South (Север-Юг) — Внешний трафик**

Это потоки данных, которые входят в вашу систему из открытого интернета или выходят наружу. На архитектурных схемах внешних клиентов (смартфоны, браузеры) принято рисовать в самом верху («Север»), а внутренние сервера — внизу («Юг»). Когда пользователь нажимает кнопку в мобильном приложении и отправляет запрос на сервер — это классический трафик North-South.

**East-West (Восток-Запад) — Внутренний трафик**

Это общение микросервисов, баз данных и других внутренних компонентов кластера между собой. Сервера внутри контура сети на схемах обычно выстраивают в горизонтальный ряд, поэтому обмен данными между ними — это движение по горизонтали. На один внешний запрос типа North-South в микросервисной архитектуре могут генерироваться десятки и сотни внутренних запросов East-West.

Для оптимизации, маршрутизации и защиты этих двух потоков требуются принципиально разные инструменты, эволюцию которых мы рассмотрим ниже.

## 1. Базовый уровень: DNS (Domain Name System)

Исторически первый и самый простой способ связать понятное имя сервиса с его сетевым адресом.

* **Как это работает:** Клиент запрашивает IP-адрес для имени `payment-service.local` у DNS-сервера, получает адрес (например, `192.168.1.50`) и отправляет запрос напрямую.
* **Где применяется:** На верхнем уровне архитектуры для управления входящим из интернета внешним трафиком (**North-South**), а также в статических корпоративных сетях.
* **Ограничения:**
  * **Проблема кэширования (TTL):** DNS-ответы агрессивно кэшируются операционными системами и провайдерами. Если микросервис упал и поднялся на новом IP, клиенты еще долго будут стучаться по старому адресу.
  * **Отсутствие портов:** Классический DNS возвращает только IP-адрес, но не знает, на каком порту запущено приложение (что критично, если на одной машине крутятся разные сервисы).
  * **Слепота к состоянию (Health Checks):** DNS-сервер продолжит выдавать IP-адрес упавшего сервера, пока администратор не удалит его вручную.

## 2. Инфраструктурный реестр: Service Discovery

Чтобы решить проблему динамических IP-адресов в облаке, на уровне инфраструктуры применяется механизм **Service Discovery (Обнаружение сервисов)**. Это «умная телефонная книга» внутри вашей сети.

* **Как это работает:** Каждый микросервис при старте автоматически регистрируется в сетевом реестре, передавая свой текущий `IP:Порт`. Инфраструктура постоянно опрашивает сервисы (Health Checks). Если сервис не отвечает, его адрес мгновенно удаляется из списка доступных.
* **Варианты реализации:**
  * **Прямой опрос реестра:** Сетевой клиент сам обращается к реестру, забирает список живых IP-адресов целевого сервиса, выбирает один из них и делает запрос.
  * **Опрос через маршрутизатор (Server-Side):** Клиент отправляет запрос на стабильный виртуальный адрес или локальный прокси-балансировщик. Этот прокси сам идет в реестр за актуальным IP и перенаправляет трафик (так работают, например, *Kubernetes Services*).
  Хотя это сильно напоминает API Gateway, но есть отличия, например Server-Side управляет трафиком East-West (внутри кластера), а API Gateway предназначен для управления входящим трафиком North-South.
* **Где применяется:** Внутреннее взаимодействие между микросервисами в кластере (**East-West** трафик).
* **Ключевые инструменты:** HashiCorp Consul, Netflix Eureka, Apache ZooKeeper.

## 3. Граница системы: API Gateway (Шлюз API)

Когда внешних микросервисов становится много, открывать их все наружу небезопасно и неудобно для фронтенд-разработчиков. Для этого на входе в кластер ставится **API Gateway**.

* **Как это работает:** Это выделенный прокси-сервер, являющийся **единственной точкой входа** для всех внешних клиентов. Трафик физически проходит сквозь него. API Gateway принимает внешний запрос, авторизует его, может изменить заголовки или трансформировать данные, динамически запрашивает внутренний адрес у инфраструктуры и проксирует запрос бэкенду.
* **Где применяется:** На границе между внешним миром и внутренней сетью микросервисов для обработки входящего трафика (**North-South**).
* **Полезные функции:** Аутентификация и авторизация (JWT, OAuth), ограничение частоты запросов (Rate Limiting), SSL-терминация, логирование, защита от DDoS.
* **Ключевые инструменты:** Kong, Apache APISIX, Traefik, Spring Cloud Gateway, AWS API Gateway.

## 4. Продвинутый уровень сети: Service Mesh (Сервисная сетка)

Когда микросервисов становятся сотни, логику повторных попыток (Retries), шифрования трафика внутри сети (mTLS) и продвинутой балансировки становится тяжело администрировать. Паттерн **Service Mesh** полностью выносит управление трафиком на уровень сетевой инфраструктуры.

* **Как это работает:** Рядом с каждым экземпляром вашего микросервиса разворачивается крошечный сетевой прокси-сервер (паттерн **Sidecar**). Приложения больше не общаются друг с другом напрямую. Сервис делает обычный HTTP-запрос, его локальный прокси перехватывает трафик, связывается со слоем управления (Control Plane), получает актуальную карту сети от Service Discovery и сам безопасно передает запрос на прокси целевого сервиса.
* **Где применяется:** Крупные, высоконагруженные распределенные системы со строгими требованиями к безопасности и наблюдаемости для точечного контроля внутреннего (**East-West**) трафика.
* **Полезные функции:** Взаимное шифрование (mTLS) на сетевом уровне, умная маршрутизация (например, Canary-релизы или А/В тесты силами сети), паттерн Circuit Breaker (предохранитель), детальная аналитика сетевых задержек.
* **Ключевые инструменты:** Istio, Linkerd, Consul Connect (на базе Envoy proxy).

## Справочная таблица: Краткий гид по технологиям

| Технология | Главная задача | Зона ответственности (Трафик) | Трафик сквозь себя |
| :--- | :--- | :--- | :--- |
| **DNS** | Преобразование домена в IP | На уровне всей сети / Интернет (**North-South**) | Нет (только выдает IP) |
| **Service Discovery** | Динамический учет живых `IP:Порт` сервисов | Внутри кластера (**East-West**) | Нет (только справочник) |
| **API Gateway** | Защита, авторизация и единый вход в кластер | На границе системы (**North-South**) | **Да (физический прокси)** |
| **Service Mesh** | Инфраструктурное управление связями и безопасностью | Внутри кластера (**East-West**) | **Да (через Sidecar-прокси)** |

## Инженерные нюансы: Что изучать при погружении в тему

Описанная выше картина — это концептуальная ментальная карта. В реальном продакшене каждая из этих технологий скрывает глубокие архитектурные нюансы, которые необходимо изучить для проектирования отказоустойчивых систем уровня Senior.

Если вы планируете внедрять эти паттерны, обратите внимание на следующие темы для самостоятельного изучения:

* **DNS на самом деле сложнее:** Классический DNS действительно ограничен, однако современные провайдеры (например, AWS Route 53) поддерживают DNS Failover с проверкой здоровья (Health Checks). Кроме того, существуют **SRV-записи**, которые умеют возвращать и IP, и порт. Важно помнить, что даже при `TTL = 0` многие клиенты (JVM, среды исполнения .NET, кэш операционной системы) кэшируют DNS-запросы намертво на уровне процесса, что делает DNS непригодным для сверхбыстрого переключения микросервисов.

* **Алгоритмы Client-Side Load Balancing:** Изучая Service Discovery по схеме «прямого опроса реестра», разберитесь, как клиент выбирает конечную ноду. Популярные библиотеки реализуют клиентскую балансировку (Round Robin, Random, Least Connections, весовые коэффициенты), перенося вычислительную нагрузку по распределению трафика с центрального сервера на сам микросервис.

* **Устройство сети в Kubernetes:** Kubernetes Services работают не как выделенный прокси-сервер в космосе. Компонент `kube-proxy` настраивает правила **iptables** или **IPVS** на уровне ядра Linux прямо на каждой физической ноде кластера. Трафик перенаправляется мгновенно на уровне ОС, а не прыгает через промежуточные сетевые узлы.

* **Интеллектуальная маршрутизация L7 в API Gateway:** Не путайте базовый Ingress (L4/L7 проброс портов) и полноценный API Gateway. Современный шлюз работает строго на прикладном уровне (L7 модели OSI) и позволяет настраивать маршрутизацию на основе бизнес-логики: например, проверять HTTP-заголовки, куки или ID пользователя, чтобы перенаправлять премиум-клиентов на выделенные, более мощные пулы серверов.

* **Обратная сторона Service Mesh (Накладные расходы):** Сервисная сетка — это дорого. Концепция Sidecar-прокси (когда Envoy сидит в каждом поде) забирает до 15-20% ресурсов процессора и памяти кластера и добавляет задержки (Latency), так как запрос проходит через два дополнительных прокси-узла.

* **Современный тренд — Прощание с Sidecar:** Изучите концепцию **Ambient Mesh** и технологию **eBPF** (на базе таких инструментов, как Cilium или Istio Ambient). Индустрия активно уходит от тяжелых Sidecar-контейнеров, перенося логику Service Mesh напрямую в пространство ядра Linux. Это позволяет шифровать и маршрутизировать трафик East-West вообще без прокси-контейнеров внутри ваших подов.

## Заключение

Выбор архитектурного подхода зависит от масштаба вашей инфраструктуры и структуры ее потоков. Для небольшого проекта часто достаточно возможностей встроенного DNS в Kubernetes или Docker Compose. По мере роста требований к безопасности внешнего периметра (North-South) незаменимым становится API Gateway. Когда же связи между внутренними сервисами (East-West) становятся слишком сложными, а сетевые политики тяжело контролировать — приходит время для внедрения Service Mesh.
